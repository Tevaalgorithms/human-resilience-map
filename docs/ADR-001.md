# ADR-001: Python application and deterministic GIS on AWS

Date: October 4, 2026  
Status: Proposed implementation decision  
Scope: Extreme heat resilience V1 for one metro area

## Context

Human Resilience Map combines demographic, heat, canopy, transport, and cooling-resource data to identify vulnerability and compare interventions. The user prefers Python and plans to host the application on AWS. Spatial calculations and scenario optimization must be reproducible, while natural-language interaction must remain grounded in checked data.

The first release needs an interactive map, tract explanations, asynchronous cooling-center scenarios, and traceable evidence. Pilot geography, usage, availability requirements, and the LLM model remain undecided.

## Decision

1. **Python application stack:** Dash/Plotly for the Python-authored frontend, FastAPI for the API, and Python analytical workers. Dash browser components use JavaScript internally; SQL and infrastructure configuration remain necessary. This supersedes the earlier React proposal.
2. **GIS storage and artifacts:** RDS PostgreSQL/PostGIS for versioned spatial inputs, metadata, and results; private S3 for raw snapshots, rasters, and exports. Publish validated dataset releases and pin each scenario to an immutable input version.
3. **Deterministic analytical core:** PostGIS, GeoPandas and raster libraries handle spatial analysis; a versioned Python scoring module calculates the resilience index; OR-Tools handles constrained site selection. Record parameters, solver status, assumptions, and non-duplicated coverage. Routing requires a separately selected data/engine solution.
4. **LangGraph orchestration:** Use typed tool calls for planning, clarification, execution, and explanation. Persist checkpoints in PostgreSQL. Data-retrieval nodes can be ordinary Python code; an LLM is not required at every step. Bedrock is the proposed inference provider, with model selection based on evaluation and regional availability.
5. **Independent verification:** Programmatic checks validate data, calculations, constraints, and solver outputs before publication. Check narrative claims against structured evidence and provide a deterministic summary when explanation checks fail. Human planners review operational site feasibility.
6. **AWS containers and queued analysis:** ECS Fargate runs UI, API, workers, and scheduled ingestion. Use a public HTTPS Application Load Balancer, private application/database networking, SQS plus a dead-letter queue, and an outbox dispatcher for reliable job submission. Workers use atomic claims, idempotent writes, and retry-safe checkpoint recovery.
7. **Identity and operations:** Cognito authentication; API checks identity and job ownership. Use shared server-side sessions, task IAM roles, Secrets Manager, CloudWatch, and Python CDK infrastructure. Keep analytical requests bounded and impose job/runtime/token limits.

## Alternatives considered

| Alternative | Tradeoff and disposition |
| --- | --- |
| React/MapLibre frontend | Greater freedom for advanced map interactions, but adds TypeScript/JavaScript development. Revisit if Dash map performance or UX limits are demonstrated. |
| Streamlit UI | Rapid prototype option; Dash is proposed for the planned map, controls, and callback-driven dashboard. |
| Single Python application/container | Simpler prototype, but long GIS jobs compete with UI/API requests. Retain separate worker execution and explicit module boundaries. |
| Lambda for all analytical work | Attractive for short event-driven tasks; execution limits and geospatial dependency packaging make Fargate the initial choice for variable-duration GIS and solver work. |
| Single EC2 host | Could lower a small pilot's bill; introduces host maintenance and a shared failure point. Remains a possible budget-driven deployment alternative requiring a revised ADR. |
| LLM-generated calculations or unrestricted SQL | Makes results difficult to validate. Use approved analytical tools with structured inputs and outputs. |
| Multi-hazard V1 | Expands data and validation requirements. Complete the heat workflow before adding hazards. |

## Consequences

Benefits: most application logic shares Python; heavy analysis is isolated from the UI; results retain source and model versions; AWS services support independent scaling and managed storage.

Costs and limitations: several services create an always-on baseline; private-network egress costs can be significant at pilot scale. Dash sessions must work across replicas. PostGIS, Python GIS dependencies, solver behavior, and model explanations require meaningful validation. A single-replica, Single-AZ pilot does not provide production availability. A tract-level planning index does not establish individual risk or predict health outcomes.

## Rollout and acceptance

Start locally, then deploy one limited-access pilot. Validate a known baseline and one complete cooling-center scenario before broader use. Acceptance requires reproducible scores, no double-counted coverage, explicit infeasible/missing-data outcomes, authorized result access, duplicate-message resilience, and grounded explanations.

The initial planning budget is about **$210–$310/month for the pilot**, including contingency; see [cost estimate](COST_ESTIMATE.md). This is an estimate, not a spending authorization or quoted AWS bill.

## Review triggers and open decisions

Review this ADR when map payloads or callbacks become too slow, solver jobs exceed the allotted resources, the database becomes a bottleneck, availability needs exceed pilot assumptions, or actual monthly cost materially exceeds the estimate.

Before deployment, select region, pilot geography, database class, routing approach, Bedrock model, backup/recovery targets, and required availability. Confirm prices and load-test representative GIS jobs. A production rollout requires a separate capacity and availability review.
